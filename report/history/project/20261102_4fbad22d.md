# 语音再次超时：原因、本次改动与当前状态

整理日期：2026-11-02。依据本轮直接读取的 SD 卡、板端文件哈希、实际采样指标和识别结果整理。

## 目前确认到哪里

当前打开的是临时 little 解码对照界面。用户确认可以识别，板端也读回了成功结果：

- 识别文字：`记录 电压 三 点 三 伏`。
- 解析结果：电压 `3.3 V`，`intent=record_manual`，没有拒绝原因。
- 这句音频长 4.08 秒，识别耗时约 2.345 秒。

这证明当前这次运行已能收音、分句、识别和解析。本轮没有验证重启后的恢复，也没有把临时方案写进正式安装包。

## 一开始为什么“语音送不进去”

实际链路是：麦克风原始字节 → PCM 解码 → 按声音和静音分出完整句子 → Vosk 识别 → 确认后保存、显示历史。

这次超时发生在“形成完整句子”这一环。采集流本身有数据，原始帧在推进，但正式版固定选择的 `msb-first` 不适合本次收到的字节排列，解码后产生持续的高能量信号。

本轮对同一批左声道原始数据做了两种解释：

| 解码方式 | RMS 中位数 | 超过原声音门限 0.01 的帧 |
| --- | ---: | ---: |
| 正式版固定的 msb-first | 0.578883 | 195/195 |
| 本次临时改用的 little | 0.008420 | 95/195 |

固定 msb-first 时，所有观察帧都被当成声音，分句器无法等到连续 0.8 秒的句尾静音，没有完整语句入队，界面最终提示“25 秒内未收到完整语音”。这种情况下 Vosk 还没有拿到本轮待识别的完整句子。

昨天原始数据的表现相反：little 会把安静解释成高能量信号，msb-first 能区分安静与说话；当时切换后也确实通过了界面识别和保存。昨天将这次可用的方式固定下来时，没有完成重启后的采集兼容性验证。这是之前固定版本时漏掉的验证。

**已经确认故障机制，但还没有查明为什么两次采样的字节分布不同。** 目前不能把触发原因断言为某个寄存器、SD 卡操作、驱动变化或硬件损坏。

## 本次到底改了什么

本轮没有覆盖板上正式源码，核心改动发生在临时 Python 后台进程内：

```python
# 2026-11-01 正式文件中的固定调用
board_mic._decode_s24le(raw, 2, channel=self.args.mic_channel, byte_order="msb-first")

# 本轮临时后台在内存中使用的调用
board_mic._decode_s24le(raw, 2, channel=self.args.mic_channel, byte_order="little")
```

临时进程同时把 PCM 布局元数据标为 `s24-le-low24-in-4`。这两处调整没有写回正式 `board_listen.py`。

为核对后续 `[unk]`，临时后台另外保留了最多三次按钮请求实际送去识别的短音频、原始 PCM 和诊断 JSON。调试文件在板内 `/home/root/labmate_audio_debug/recognition_probe_15dd06494b4c`，与普通实验历史分开；实验历史仍由原有确认操作保存。

Qt 二进制、后台业务代码、模型、词表、解析和历史记录逻辑都没有修改。采集仍为 hw:0,1、44100 Hz、双声道 S24_LE，选左声道 0；声音门限仍为 0.01，句尾静音仍为 0.8 秒。麦克风初始化沿用原程序。

临时入口位于 `/tmp/labmate_little_trial_k7imknod/backend_trial.py`，退出后由监督进程清理；正式入口文件仍是此前冻结版本。**因此不能把当前成功理解为新版已经正式下载或重启后必定可用。**

## 为什么中间出现了 [unk]

切换 little 后有了完整语句进入识别，但最初两次没有得到可信结果：第一句为 `[unk]`，第二句包含错误数字和 `[unk]`。第三句在同一后台进程、同一解码和同一识别参数下，正确得到 `3.3 V`。

这期间没有再次修改模型、词表、门限或保存逻辑。现有证据不足以确定前两句失败的具体音频原因，不能把第三句成功说成又加了某项识别算法修复。

## SD 卡是否真的有问题

有独立的读取异常。对照昨日完整备份，974 个可读取文件全部匹配；23 个文件报 Windows 1392“文件或目录损坏且无法读取”，还有三个目录无法枚举，令另外 272 个文件无法核验。这里的 295 个文件是“无法核验”，不等于全被删除。

读取失败的项目包括 SD 上原语音工程的 `board_listen.py`、`asr_grammar.py`、原 ZIP，以及两个仪器目录。SD 上 14 个模型文件仍正常匹配。本轮没有修复或改写 SD 卡，昨日备份仍在电脑上。

板内当前正式部署的 20 个文件、14 个模型文件和 Vosk 库均通过哈希校验，路径也没有跳转到 SD 卡。当前超时不能归因于正式程序漏传；SD 读取问题需要另行处理，现有证据没有证明它引起了采样排列变化。
