# 给 ARM 同学的 SPI 图片功能交接清单

日期：2026-11-04

目标：保留现有语音、界面、仪表通信与摄像头硬件，将摄像头单帧图像压缩成 JPEG，通过新增 SPI 接口发送给 ESP32-WROOM。当前不开发 FFT。

## 一、你需要交给 ARM 同学的文件

已整理为本交接包；优先让他阅读 `ARM端交接_SPI图片发送.md`。

| 文件 | 作用 | 对方需要做什么 |
|---|---|---|
| `FPGA/asr_esp32_spi.xsa` | Vivado 2020.2 导出的新硬件描述，包含 PS 配置、硬件地址和初始化信息 | 用于核对硬件、生成匹配的 FSBL；不需要他重新设计 FPGA |
| `FPGA/asr_esp32_spi.bit` | 已完成综合、布局布线和时序检查的 FPGA 配置文件 | 双方联调时使用同一版；你可以负责 JTAG 下载 |
| `linux/esp32-spi.dtsi` | SPI0 启用和原 UART1/CAN0 禁用的设备树片段 | 合入实际使用的设备树，编译匹配的 dtb/启动文件 |
| `linux/add_spidev_match.py` | 在匹配内核源码的 spidev 驱动中增加本设备 compatible | 检查驱动绑定方式；需要时修改并编译匹配内核/模块 |
| `linux/send_jpeg.py` | Python3 单张 JPEG 发送程序，含分包、READY 令牌和 CRC 确认 | 先独立运行，再接入应用工作线程 |
| `linux/qt_send_example.cpp` | 从已有 QImage 缩放、编码 JPEG 并调用发送器的 Qt 示例 | 结合现有摄像头采集和界面代码集成；它不是完整摄像头程序 |
| `linux/check_board.sh` | 只读检查内核、SPI、GPIO 和视频设备 | 在板卡运行并反馈输出，确认实际系统情况 |
| `SPI协议.md` | Zynq 与 ESP32 的报文、确认和握手约定 | ARM 和 ESP32 使用同一版本，不自行改变其中一端 |
| `test_320x240.jpg` | 320×240 彩条测试 JPEG | 摄像头接入前，先用它验证文件传输 |
| `接线与下载说明.md` | 接线、跳帽、临时 PS 时钟初始化、编译和下载方法 | 联调时对照执行；接线和 FPGA 下载建议由你负责 |

不必优先发送完整 Vivado 工程。只有对方需要检查或修改 FPGA 时，再给完整工程包。XSA 和 bit 不应与其他 FPGA 版本混用。

## 二、你还需要明确告诉他的硬件约定

数据路径：

`摄像头 → 原厂 PL 采集/帧缓存 → DDR → ARM 采集及 JPEG 编码 → Linux SPI 驱动 → PS SPI0 经 PL 引出 → ESP32`

- 新接口使用 **PS SPI0，地址 e0006000，CS0**。PL 做 I/O 引出，当前没有硬件 JPEG 编码器或专用 PL 图片 DMA。
- Zynq 为 SPI 主机，ESP32-WROOM 为从机；mode1、8bit、MSB first、CS 低有效。先请求 2 MHz，实际频率会受 PS 分频影响。
- 单张 JPEG 最大 65536 字节；初期建议 320×240、质量 60、按需发一张。
- READY 使用 **EMIO11，即 PS GPIO 控制器线偏移65**；Linux 全局 GPIO 编号需加 gpiochip 的实际 base，不能直接认定全局编号就是65。
- READY 为每个就绪事务翻转一次的令牌，**不是普通“高电平就一直可发”的握手**；发送器已实现该约定。
- 新增 SPI 借用了原 UART1 和 CAN0 的引脚，这两项需要在 Linux 设备树禁用。USB 调试控制台 UART0 保留。
- 原摄像头、LCD、触摸、音频、网口及原 AXI 地址保留；不要为加入 SPI 整体替换原设备树。

接线对照：

| 信号 | Zynq 端 | ESP32 GPIO |
|---|---|---|
| SCLK | J3-1 / K14 | 18 |
| MOSI | J3-2 / M15 | 23 |
| CS_N | J3-3 / J14 | 27 |
| MISO | J3-4 / L16 | 19 |
| READY 令牌 | U4-2 / KEY / G14 | 26 |
| GND | J3-37 或 J3-39，或 U4-5 | GND |

接线前断电，移除 P1 串口选择跳帽及 P3 两个 CAN 跳帽，U4 不插其他模块。ESP32 开发板独立 USB 供电并共地，具体以接线说明为准。

## 三、建议的职责划分

| 工作 | 建议负责人 | 交付/验收结果 |
|---|---|---|
| FPGA 工程、bit/XSA 版本与引脚维护 | 你 / FPGA 侧 | 提供本包对应版本；修改接口后同步更新协议 |
| 领航者与 ESP32 接线、跳帽和 FPGA JTAG 下载 | 你 | 接线符合表格，Linux 启动前已加载正确 bit |
| ESP32 接收固件编译烧录 | 你或 ESP32 负责人 | 接收端已运行并能给 READY 令牌，收到图后输出长度及 CRC |
| Linux 设备树、SPI/驱动匹配、PS SPI 时钟与启动适配 | ARM/Linux 负责人 | SPI 设备出现，内核/模块版本匹配，GPIO 可读，原功能正常 |
| 摄像头单帧采集、像素格式转换与 JPEG 编码 | ARM 负责人 | 获得不超过64KiB的有效 JPEG |
| 发送程序接入语音命令、界面和工作线程 | ARM 负责人 | 一次一个任务，界面不阻塞，明确显示成功/失败 |
| 联调及性能记录 | 双方 | 文件传输先通过，再接摄像头；分别记录采集、编码、发送耗时 |

如果 ARM 同学只负责 Qt/Python 应用、没有负责 Linux 系统构建，第三方 Linux 底层适配需要单独指定人员承担，不能只给他一个发送脚本就认为准备完成。

## 四、当前你已经能给的，以及尚未给出的

**已经能给：**本包全部文件、已通过实现和时序检查的 bit/XSA、接口约定、接收端源码在完整工程包中的位置、主机协议测试结果。

**当前没有：**针对板卡实际运行系统编译并验证好的新 `system.dtb`、`image.ub`、`spidev.ko`、`FSBL.elf` 或 `BOOT.BIN`。因此本包不是一个“全部复制到 SD 卡就能运行”的系统镜像。

ARM/Linux 负责人需要从当前板卡及配套工程确认：

1. 当前内核版本与配置，是否已启用 Cadence SPI、spidev 和 sysfs GPIO。
2. 实际加载的是哪份 dtb/image.ub，以及对应设备树源码和构建工程。
3. 与当前内核匹配的源码、配置和交叉编译工具链是否齐全。
4. 摄像头视频节点、输出像素格式、分辨率及当前是否被其他程序占用。
5. 当前启动方式和启动脚本是否会再次加载旧 bit。

这些信息应以实际运行系统为准。你若持有当前 SD 卡启动文件、原厂 Linux/PetaLinux 工程和已知启动日志，一并发给他；如果没有，让他在板卡上确认并列出缺少的材料，再补齐。

仅下载新 bit 不会执行新的 PS 时钟初始化。正式部署需匹配初始化与设备树；临时联调可参考接线说明在 U-Boot 中仅配置 SPI 时钟。不要在已运行 Linux 中执行整套 ps7_init。

## 五、让 ARM 同学按这个顺序推进

1. 阅读交接文档，运行 `check_board.sh`，确认当前 Linux 环境并列出缺项。
2. 与你核对接线、FPGA 版本和 ESP32 固件，完成 SPI 时钟、设备树及驱动准备。
3. **先发本包 test_320x240.jpg**，ARM 输出 delivered，ESP32 输出相同长度和 CRC。
4. 接入摄像头，生成同样符合限制的 JPEG，再复用发送器。
5. 最后接语音命令与界面，放到工作线程；验证原语音、触摸、显示及仪表通信正常。

请他返回：实际 SPI 设备路径、PS gpiochip base/READY 路径、采用的设备树和初始化方式、发送测试日志、摄像头格式，以及采集/编码/传输的分别耗时。

## 六、验证边界

FPGA 已完成 Vivado2020.2 综合、布局布线和受约束路径的时序检查；交付 ZIP 经异地解压检查，工程依赖文件齐全。协议通过79项主机测试。

当前未完成板上端到端传图，也未在本环境构建完整 ESP-IDF 固件。完整工程中的 ESP32 示例默认将 JPEG 存入 RAM 并打印长度/CRC，不自动显示、保存 Flash 或通过 Wi-Fi 转发；若需要这些功能，应由 ESP32 负责人另行接入。
